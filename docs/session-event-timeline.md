# 会话事件时间线：目标轮次不产生 turn/end

## 现象与判据

用 [`experiments/read-turn-timeline.mjs`](../experiments/read-turn-timeline.mjs) 直接读会话持久
日志（`~/.dsh/sessions/*/session.v4.jsonl.zstd`）得到：

```
turn/start = 21   turn/end = 20
最后：turn/start turn=21 @16:27:24 —— 尚无配对的 turn/end
```

即：**目标（goal）的自动延续轮次不结束轮次**，它是同一个轮次内的连续驱动。

## 对用户预期的影响

「一轮结束」这类通知依赖 `turn/end`。因此：

- **目标跑多轮时，`turnEnd` 通知不会在轮次之间触发**，而是等到整个目标完成、
  被暂停、或出错时才响一次。
- 这不是插件的缺陷，是驱动方式的结果。但它会让人以为「插件没在工作」。

这一点值得写下来，因为**从外面看，「事件没发生」与「插件没收到」完全一样**。
没有日志时间线的话，只能靠猜。

## 怎么区分这两种情况

| 现象 | 结论 |
| --- | --- |
| 持久日志里有 `turn/end`，但信号表里没有 | **插件的缺陷** |
| 持久日志里没有 `turn/end` | 事件本就没发生，与插件无关 |

`read-turn-timeline.mjs` 就是做这个判定的工具。

## 日志格式（别照标准 zstd 流写）

文件是**多个独立 zstd 帧顺序拼接**：第一帧是会话头，之后每帧含若干 JSONL 事件。

因此：

- `zstdDecompressSync(整个文件)` **只解出第一帧**——最初让我误以为日志里只有 1 条事件；
- `createZstdDecompress()` 的流式解压会在第二帧报 `Unknown frame descriptor`——
  它不是单条 zstd 流。

正确做法是按魔数 `28 b5 2f fd` 定位每个帧、逐帧独立解压再拼接。实测本会话文件有
2822 个帧、4381 条事件，全部解出。

## 顺带确证的一件事

日志里存在 `turn/end … reason=error`（`turn 15`，16:02:54）。它没有出现在信号表里，
但**这不是缺陷**：插件最早记录是 16:14:23，那次事件早于观察者。

按上面的判据表，这属于「事件发生了但插件还没挂载」——第三种情况，也需要能区分。
