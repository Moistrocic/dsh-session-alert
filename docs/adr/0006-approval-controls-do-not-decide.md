# ADR 0006 — 审批控件不代用户提交决定

状态：已接受（**修订 ADR 0003 的技术假设**）

## 背景

[ADR 0003](./0003-approval-controls-answer-on-the-users-behalf.md) 决定：审批卡片上的
**批准 / 拒绝**按钮**代用户把决定提交给 DSH**。当时把它当作一个「有明确技术路径、
只是需要实现」的功能。

实现阶段查证 `approval` 服务的真实契约后，这个假设不成立：

```
approval.request(req: ApprovalRequest): Promise<ApprovalOutcome>
```

它的说明里有三条关键约束：

- *"Ask the composed answerers to decide one readonly same-process request."*
  —— 它是**请求方**调用 answerer 的入口，不是「一个可以被外部注入决定的开放问题」。
- *"The request requires an open turn because the audit pair must be enclosed by the
  durable log's commit/replay boundary; an idle ask rejects before appending anything."*
  —— 决定必须落在一个**开放中的轮次**内，否则直接拒绝。
- *"A failure that prevents either audit append from committing still rejects because
  returning an unlogged decision would violate the pair."*
  —— 每个决定都要与它的审计记录成对提交。

而本插件的处境是：**一个在轮次之外运行的外部进程**（通知由 Windows 投递，点击由协议
激活的独立启动器接收）。它既不在那个开放轮次里，也不在那个进程内。

## 决定

**审批卡片不携带任何代用户做决定的控件。** 按钮只把用户带到待批准提示面前，
由用户在界面里做出决定。

具体而言：

- 审批场景的卡片**不带确认按钮**（这一点仍遵循 ADR 0002，因为「确认收到」在审批语境下
  没有意义）；
- 但它也**不提供「批准 / 拒绝」**。改为一个把窗口带到最上层的按钮，文案明确写成
  「去处理…」而不是「批准」，**让文案与实际行为一致**；
- 通知正文必须说清是哪个工具在等批准，使用户能判断这件事值不值得过去看一眼。

## 后果

- **ADR 0003 的「代答」部分被本 ADR 取代。** 它当初的顾虑（「插件可以放行用户从未读过的
  操作」）依然有效，但结论从「用设计义务约束它」变成了「干脆不给这个能力」——
  后者更简单也更安全：不存在能代答的代码，就不会有代答失控的可能。
- **ADR 0003 中关于「决定必须绑定到恰好一个请求」「过期卡片 fail closed」「沉默绝不是
  同意」的约束不再需要实现**，因为不再有插件发出的决定。它们作为**记录**保留，
  说明当初为什么否掉了若干替代方案。
- 通知的**正文**因此承担了更重的责任：既然按钮不能替用户判断，正文就必须让用户
  看清楚在等什么。这与 ADR 0002「通知必须承载足够的会话信息」是同一条理由。
- 用户从通知到完成批准需要两步（点按钮 → 在界面里点批准），比原设想多一步。
  这是安全边界的代价，且这一步恰恰是「人在回路里」真正发生的地方。

## 考虑过的替代方案

- **想办法在轮次内、进程内注入决定**（例如注册一个 answerer、或让插件参与
  `approval.request` 的组合）。已否决：那等于让插件成为审批链的一环，而它的输入来自
  一个外部进程（Windows 通知）。把一个外部进程接入审计边界内，正是这套机制要防的事。
- **把请求 id 放进 URL，由启动器回调 Host 提交决定。** 已否决：`request` 要求开放中的
  轮次，而用户点击通知的时刻可能已经不在那个轮次里；这种情况下「提交」要么被拒，
  要么——更糟——落到另一个恰好开放的请求上。ADR 0003 已明确「决定必须绑定到恰好一个
  请求，过期卡片 fail closed」，而这条通道做不到这个保证。
- **按钮只做「确认收到」。** 已否决：审批语境下确认没有意义，而且会让审批卡片与普通
  卡片无法区分，用户会以为自己在批准什么。
