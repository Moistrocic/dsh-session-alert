# ADR 0001 — 端别由客户端自报，且只决定宣告的形状，不决定目的地

状态：已接受（本文是该决定演进后的**一致最终形态**，末尾记录了演化过程）

## 背景

Host 正在运行时，某个 Session 可能需要用户介入，而有三种形态：

1. **desktop** 应用在运行。它只要在运行就始终挂接着 Host——最小化窗口不会断开挂接。
2. 挂接了一个或多个 **web** 客户端（一个浏览器页签，也可能多个，或来自另一台机器、经隧道访问的浏览器）。web 客户端可以自由挂接与断开，且可以同时挂接多个。
3. **两者都没挂接**：用户关掉界面走开了。

Host 自己答不出当前属于哪种形态。它的请求身份里没有端别判别字段——`AccountClientMetadata` 只带 `version`、`locale`、`timezoneOffsetSeconds`——而且根本不存在 `notification` 服务。账号登录路径上确实有个 `loginSource: 'web' | 'desktop'` 参数，这证明 DSH 把两者当作一等类别，但它是发起调用的界面**逐次**填的，不是一个可读取的环境事实。

唯一真正知道自己端别的是客户端。唯一能观察到每一次 Session 状态变迁的是 Host。

## 决定

### 一、端别由客户端自报确定

客户端半边自行判断自己运行在 DSH web 客户端还是 DSH desktop 客户端中，并通过既有的包内 RPC 通道把这一事实上报给同包的 Host 半边。Host **不**从环境变量、profile 路径或 bundle 来源推断端别。

**端别是范畴性的，不按窗口。** 可以同时挂接多个 web 客户端，本插件不在它们之间作区分；它只区分 `web` 与 `desktop`。

### 二、端别决定宣告的形状，不决定目的地

两种端别都经 **Host 自己的 Windows 通知通道**投递。端别**不**选择一条投递通道，而是选择**卡片形态**：

| 触发时挂接的端 | 发出的形态 |
| --- | --- |
| `desktop`（无论是否同时有 `web`） | 完整卡片——可点击，带控件。 |
| 仅有 `web` | web 形态——无控件。 |
| 两者皆无 | web 形态——无控件。 |

理由：desktop 卡片是 web 形态的**严格超集**——它包含 web 形态的一切，外加控件。既然两种端别都由同一条 Host 通道送进同一个通知中心，同时宣告两次只会让一个事件在屏幕上出现两条几乎相同的通知。因此当 desktop 客户端在线时，web 形态没有任何可补充的东西。

**必须保住的保证：为「仅 web 受众」发出的卡片，绝不能携带控件**——因为不存在一个能产生该控件所隐含决定的客户端。

### 三、在线语义在两端之间不对称

- **`desktop` 的在线是有意义的**：desktop 应用只要在运行就挂着，所以「是否有 desktop 客户端挂接」是一个有真实答案的真实问题。
- **`web` 的在线不是闸门**：web 客户端数量无上界、可自由挂接，所以它只影响卡片形态，不影响是否宣告。
- **客户端缺席永不压掉宣告。** 两者皆无时照常发出。用户走开的情形恰恰是最值得打断他的情形。

## 后果

- 插件有两个半边，且 Host 半边必须能在**完全没有客户端挂接**时完整工作——那是它最重要的运行形态，不是降级形态。
- 在线需要一个存活概念，而不只是一个「曾经挂接过」的标志，否则崩溃的客户端会被永远当作在线。**在线会过期。**
- 端别在**卡片构造**处被消费，因此能力边界在这一层强制，而不是在投递层。
- 因为 `desktop` 的在线有意义而 `web` 的在线没有，两者**不能**用同一套对称机制建模、再让代码到处特判。
- 投递给 web 受众的通知不需要任何跳转或聚焦动作——它只是宣告。desktop 卡片**可以**做更多。
- 将来增加第三种 Client Kind 属于**修改本决定**，而不是扩展它。

## 考虑过的替代方案

- **从 Host 环境推断端别**（`$DSH_PROFILE`、安装布局、`…/profiles/<name>` 路径）。已否决：它回答的是「加载了哪个 profile」，而不是「哪个客户端正在看我」。打包后的 Electron 应用可能呈现意外的或继承来的环境，答案会是启动时钉死的猜测，而不是投递时观察到的事实。
- **从提供客户端 bundle 的 HTTP 请求推断端别。** 已否决：Host 没有这样的判别字段，自己造一个意味着解析 user-agent 字符串；而且「哪个客户端在看」这个概念在什么都没连接时依然不可得。
- **没有客户端挂接时压掉宣告。** 已否决：它把目的倒过来了——关掉界面的用户正是最需要被告知的用户。
- **由浏览器自己弹 web 通知。** 已否决：浏览器的通知能力**不支持按钮**，会让两种端别根本无法表达各自的形态差异；而且页面与系统通知会彼此脱钩。
- **两种端别各弹一份（跨端不去重）。** 已否决：在两端共用同一条 Host 通道的前提下，这会让一个事件在同一个通知中心里出现两条几乎相同的通知。

## 演化过程

本决定被修正过一次，记录于此以免重蹈：

最初的措辞把端别当作**目的地**选择器，并断言「两个端各得一条、跨端不去重」。在用户确定 **web 端也由 Host 发 Windows 通知**之后，该推论失效——同一条通道、同一个通知中心，各弹一份就成了重复噪音。用户随即明确：**只弹一条，取带按钮的 desktop 卡片。**

需要保留的是原则而非推论：两种端别确实是**不同的产物**（一个带控件，一个不能带），代码必须分别建模，而不是当作「一条消息 + 可选装饰」。至于"各自被宣告一次"，那是我从原则里推错的一步。
