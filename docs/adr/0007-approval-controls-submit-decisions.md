# ADR 0007 — 审批控件真的提交决定（修订 ADR 0006）

状态：已接受（**取代 ADR 0006 的结论**；ADR 0003 的约束重新生效）

## 背景

用户要求审批卡片上有三个按钮：**批准 / 拒绝 / 跳转到Harness**，而且按钮必须真的有效
（本项目的一条硬规矩：文案必须与实际行为一致——写着「批准」却只把窗口带上前来，
比没有这个按钮更糟）。

[ADR 0006](./0006-approval-controls-do-not-decide.md) 当年否掉了两条路：

1. **把请求 id 放进 URL，让外部进程稍后回调 Host 提交决定。** 否决理由成立且仍然成立：
   `approval.request()` 要求开放中的轮次，用户点击的时刻可能已经不在那个轮次里；
   这种情况下「提交」要么被拒，要么落到另一个恰好开放的请求上。
2. **注册一个 answerer。** 否决理由是「那等于让插件成为审批链的一环，而它的输入来自
   一个外部进程（Windows 通知）」——把一个外部进程接进审计边界内，正是这套机制要防的事。

第 2 条的理由需要重新审视，因为查证后事实与当时的描述不同：

- 查询说明：
  > `'approval/request'( this: Scoped<Agent>, req: ApprovalRequestEvent, next: () => Promise<ApprovalOutcome> ): Promise<ApprovalOutcome>`
  > *"Ask composed answerers for one decision. Return an outcome to claim the request or call `next()` to delegate."*
- `@deepseek-ai/dsh-user-approval` 的文档同样明确：**「应答者是 `approval/request`
  waterfall 监听器」**，且「每项部署应组合一个最终应答者」。

也就是说：**本插件的 Host 半边本身就在进程内**，当它作为应答者被询问时，它**就在那个
开放轮次内**——这正是「决定必须落在开放轮次内」所要求的条件。ADR 0006 描述的
「轮次之外的外部进程」对**通知投递与点击**成立，但对**应答者**不成立：应答者不是
「稍后从外面塞一个决定进来」，而是「请求方正在等它回答」。

## 决定

**审批卡片带三个按钮（批准 / 拒绝 / 跳转到Harness），插件作为 `approval/request` 的
waterfall 应答者真的提交决定。** 机制：

1. 监听 `approval/request` 时开一个**待决令牌**（`lib/decisions.js`），把「批准 / 拒绝」
   两个按钮的 `arguments` 指向 `dsh-session-alert://decide/?token=…&decision=allow|deny`。
2. **先只等通知**（宽限期 20 秒，`DSH_SESSION_ALERT_NOTIFY_GRACE_MS` 可覆盖）。
3. 点击经协议激活落到启动器，启动器把 `{token, decision}` POST 回 `/decide`；令牌兑现，
   结果（`allowed-once` / `rejected`）作为应答者的返回值提交，由服务成对写入
   `approval/asked` 与 `approval/decided`。
4. **下面任一件事发生**就作废令牌，并**这时才**调用 `next()` 把决定权交给界面：
   宽限期到（20 秒）、**desktop 端报告获得焦点**、或请求被中止。
   卡片被抑制（用户正看着窗口）时跳过第 2 步，直接交界面。

   焦点这一条是**实测逼出来的**：用户点「跳转到Harness」时不会消费令牌（他就是要回界面
   处理），若只靠宽限期，他得干等最多 20 秒才看到批准提示 —— 反馈原话是「点了跳转，
   批准界面延迟至少 5 秒」，而那一刻他正盯着窗口。客户端半边的焦点上报是事件驱动的
   （`focus`/`blur` 后立即上报），所以这条交接是几十毫秒级。

### 为什么是「交替」而不是「两边同时」

第一版是并行：立刻 `next()` 让界面提示出现，同时等通知，`Promise.race` 取先到的那个。
**这个设计有缺陷，已被真机反馈证实**：界面提示一旦弹出，就**没有任何东西能把它收回**
——它是另一个应答者在等它自己的答案。于是通知先答之后，请求结算、操作放行，
而输入区上方那个「批准」弹框继续挂着。用户看到操作已成功却还有个可点的批准框，
**分不清是「没生效」还是「没更新」**。实测就是这么被反馈的。

交替之后，**同一时刻只有一个活的决定面**：
- 通知作答 → 界面提示从头到尾没出现过，没有残留；
- 宽限期到 → 界面提示出现，旧卡片的按钮已作废，后再点会得到启动器的
  「已失效，请在界面里作答」（诚实且指向正确的地方）。

代价：窗口未聚焦但人在机器前时，界面提示会晚一个宽限期出现。20 秒是折中值。

## 安全不变式（这些是「能代答」这件事的代价，必须逐条守住）

1. **一个令牌只绑定一个请求，且只能用一次。** 提交后立即从表里删除；重复提交一律拒绝，
   **绝不**落到「另一个恰好待批的请求」上。（ADR 0003 的原始约束，重新生效。）
2. **过期即失效（fail closed）。** 请求结算、用户中止、卡片没发出去、超过有效期
   （10 分钟）——令牌都不再可用。
3. **沉默绝不是同意。** 通知那侧超时或失效时，它的 promise **永不兑现**，race 只能由界面
   那侧结束。没有默认放行，也没有默认拒绝，只有「交回界面」。
4. **卡片没发出去就没有令牌。** 卡片被抑制（用户正看着界面）或投递被跳过时，令牌立刻作废
   ——按钮都不在，没人能点，留着它只会让一个拿得到令牌的进程凭空获得放行能力。
5. **令牌只在内存里，也只出现在那张通知的按钮参数里。** 不落盘；`/state` 只报
   「有几个待决」与它们的会话/工具，**绝不暴露令牌**（`/state` 是本机无凭据可读的）。
6. **提交通道无凭据，令牌是唯一的关。** 128 位随机、只发进用户点得到的那张卡片。
   这不是密码学意义上的保密（通知历史就在用户目录里），而是把「放行一次工具调用」
   从「本机任何进程随手一 POST」收紧到「拿到那一次点击带回来的令牌」。

## 后果

- **ADR 0006 的结论被取代**：审批卡片不再是「去处理…」一个按钮，而是三按钮；
  它关于**外部进程稍后回调**（第 1 条路）的否决依然有效，且正是本 ADR 刻意**不采用**
  那条路的原因。
- **ADR 0003 的三条约束重新生效**（绑定唯一请求、过期 fail closed、沉默不是同意），
  它们的实现就是上面的六条不变式。
- 用户从通知到完成批准回到**一步**：直接在卡片上按「批准」。这是本次需求的目的。
- 插件因此**获得了代用户放行工具调用的能力**。这是明确接受的代价，其边界由上面六条
  不变式划定；`npm test` 里每一条都有对应断言。
