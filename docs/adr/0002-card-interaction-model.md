# ADR 0002 — 卡片的交互模型：点击即跳转，按钮语义按事件类型区分

状态：已接受

## 背景

desktop 卡片是本插件唯一带交互控件的产物（见 ADR 0001）。它必须同时承担三件事：告知发生了什么、让用户能过去处理、以及在需要授权的场景下让用户不必回到界面就能作答。

Windows toast 支持按钮与点击激活，但受 Windows **前台锁**限制：后台进程不保证能把窗口抢到前台，常见的降级表现是只闪任务栏。

## 决定

### 一、卡片本身就是跳转入口

**点击卡片** = 把 DSH 窗口提到**前台** + 在应用内切换到该 Session。跳转**不占用按钮**——按钮是稀缺资源，不应该浪费在卡片本身就该做的事上。

**分阶段交付：** 第一阶段只做「提到前台」，它一定有解；「切换到指定会话」作为增强项。

这条分期不是保守，而是证据要求的结果：

- **提到前台有解。** `dsh:` 协议已在操作系统注册，而应用持有单实例锁——第二次启动会立刻退出，已运行实例的 `second-instance` 处理器执行「最小化则还原 → 显示 → 聚焦」。所以点击卡片指向一个已注册的激活目标是可行的。
- **切换到指定会话，DSH 不提供任何外部入口。** `dsh://` 只做两个字符串的字面比较，不解析任何参数，而且在 Windows 上那个处理器根本不触发——链接在 Windows 上只是激活令牌，载荷是死数据。没有按会话寻址的深度链接，没有入站 IPC，没有 CLI 开关，DSH 自己也没有 AUMID。
- **但那个原语存在，而且在我们手里。** 它是客户端半边服务 `uiWorkspace.openSession(target)`，签名注明「选中一个 Session 并展示其对话，作为一个 UI 导航动作」，`target` 接受 `SessionId`。它的调用者全是客户端半边——**本插件的客户端半边正是其中之一**。

所以增强项的形态是：客户端半边既然已经在向 Host 上报端别，Host 就可以在同一通道上回话「显示会话 X」，由客户端半边执行切换。**须注意**：动态插件通道是**浏览器→Host 单向**的，没有 Host→浏览器的推送，所以客户端必须轮询或依托已同步的 store 状态。

### 二、普通卡片只有一个确认按钮

普通卡片的按钮**只用于确认收到**，**刻意不触发跳转**。跳转是点卡片的事。

理由：确认与跳转是两件不同的事，各有一个自然的交互载体。把确认也做成跳转会逼用户二选一——想标记「我看到了」的人被迫接受一次导航。

### 三、审批卡片没有确认按钮，改用批准/拒绝

当事件是「工具等待授权」时，卡片**不出现**确认按钮，改为**批准**与**拒绝**两个按钮，各自直接提交决定（其权限含义见 [ADR 0003](./0003-approval-controls-answer-on-the-users-behalf.md)）。

## 后果

- **确认与授权是不同概念，绝不能塌缩成同一个按钮。**「我看到了」与「我允许」分量不同。这一条同时是交互约束与安全约束。
- 卡片必须能表达三种形态：可点击无按钮、可点击带一个确认按钮、可点击带两个决定按钮。形态由事件类型选出，不由端别选出（端别只决定**有无**控件）。
- **通知必须承载足够的会话信息，才能支撑跳转。** 卡片上的文案是用户判断「这是哪个会话」的唯一依据，因此通知模板默认带上工作区名与会话名不是装饰，而是跳转这件功能的前提条件。
- 前台跳转在 Windows 上前台锁下**可能只闪任务栏**。这是已知且可接受的降级：用户仍然看得见通知、仍然能点第二次。不为了「保证置顶」而引入侵入性手段。
- 增强项落地前，用户点击卡片会被带到应用但需要自己选会话；因此增强项的验收必须单独成立，不能靠第一阶段「看起来能用」蒙混过去。

## 考虑过的替代方案

- **把确认按钮也做成跳转。** 已否决：混淆两个不同意图，并让确认动作带上不需要的副作用。
- **只做「提到前台」，放弃切换会话。** 已否决：能力就在我们自己的客户端半边里，没有理由不取。
- **用 Win32 强制抢前台**（`SetForegroundWindow`、置顶、`moveTop` 等）。已否决：DSH 只在 macOS 用强抢（`app.focus({steal:true})`），Windows 上刻意不做；跟着硬抢会与应用的既有选择相悖，且前台锁本来就会让强抢经常失败。
- **审批卡片同时保留确认与批准/拒绝三个按钮。** 已否决：审批场景下「确认收到」没有意义——决定本身就是回应，多一个按钮只会让人误点。
