# ADR 0003 — 审批控件代用户作答

状态：已接受

## 背景

当 Attention Event 的起因是「工具等待授权」时，desktop 卡片用**批准**与**拒绝**按钮取代普通的确认按钮（见 [ADR 0002](./0002-card-interaction-model.md)）。

DSH 的审批路径是一条瀑布：`approval/request` 组合若干 answerer，结果记入发起请求的 Session 日志。它的目的是在策略标记出的操作上**保留人在回路**。用户自己配置的审批策略是 `ask`。

让这两个按钮只是**确认**通知、或只是**打开应用并定位到待批准提示**，会让功能仍然有用、并且明显更安全。本 ADR 选择的是：按钮**了结**该请求。

## 决定

**在 desktop 卡片上按批准或拒绝，即把该决定作为用户对挂起 `approval/request` 的答复提交给 DSH。** 工具相应地放行或拦下。这两个按钮既不是确认，也不是导航快捷方式。

这是一次**决策权的有意转移**：插件被允许作为它**所宣告的那一个具体请求**的 answerer 行事，且仅限于那一个。

## 后果

- **插件可以放行用户从未读过的操作。** 通知是一件「扫一眼」的产物；它背后的操作可能是破坏性命令。因此卡片必须在决定可达**之前**就把挂起操作表达清楚，且按钮必须是有意为之——误点一条通知不能批准任何东西。这是卡片身上的**设计义务**，不是锦上添花。
- **这收窄了、但没有取消已配置审批策略的价值。** 策略仍然决定**哪些**操作需要询问；插件决定询问**在哪里**浮现。策略静默放行的操作永远不会到达卡片。
- **一个决定必须能绑定到恰好一个请求。** 批准必须了结被宣告的那一个挂起请求。**过期卡片**——其请求已被答复、已超时、或所属 Session 已结束——必须 fail closed，而不是去批准此刻恰好挂起的任何东西。
- **宣告发出后，审批必须仍然可答。** 卡片可能在几分钟后才被点击，早已超出发起它的代码的生命周期；因此答复路径不能依赖在途状态。
- **未被点击的卡片让请求保持挂起**，这是正确结果：**沉默绝不是同意。**
- 插件由此获得了一项它其余部分都不需要的特权，因此答复路径必须是**唯一**能触达审批服务的代码，且**绝不能**从 web 宣告路径触达。
- **与审批策略的关系：** 当前策略为 `never`，此场景因此不会触发。插件不因策略而删减此能力——策略改回 `ask` 时它应自动生效。

## 考虑过的替代方案

- **按钮只展示详情，用户在应用里决定。** 明显更安全，并保留「审批提示是唯一做决定的地方」这一性质。已否决：它放弃了功能的主要收益——不回应用就能决定。
- **按钮在应用里定位到挂起提示。** 已否决为半吊子：交互次数与直接打开应用相同，相对「仅确认」没有任何收益。
- **按钮仅作确认。** 已否决：那会让审批形态的卡片与普通卡片无法区分。
